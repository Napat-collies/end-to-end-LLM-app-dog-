## 1. Problem and Users (ครึ่งหน้า)

- **ผู้ใช้:** คนที่จะรับเลี้ยงสุนัขเป็นครั้งแรก
- **ปัญหา:** ข้อมูลสายพันธุ์กระจัดกระจาย ข้อมูลเชิงบรรยาย (นิสัย การดูแล) กับข้อมูลตัวเลข (น้ำหนัก อายุขัย) อยู่คนละที่ และ LLM ขนาดเล็กตอบตัวเลขจากความจำได้ไม่แม่น
- **คุณค่า:** คำตอบที่มีแหล่งอ้างอิงตรวจสอบได้ ตอบภาษาไทยได้ และบอกว่า "ไม่พบข้อมูล" แทนการเดา

## 2. Design (1.5–2 หน้า)

- **แผนภาพสถาปัตยกรรม:** วางโค้ด mermaid จาก README ที่ https://mermaid.live แล้ว Export เป็น PNG ใส่รายงาน
- **ตาราง "capability families" 6 หมวด:** ใช้ตารางจาก README
- **เหตุผลของการออกแบบ** เขียนเป็นข้อ ข้อละ 2–3 ประโยค
  1. ทำไมใช้ agent แทนการเขียน if-else (คำถามหลายรูปแบบ หลายภาษา บางข้อต้องใช้สอง tool)
  2. ทำไมให้โมเดลกรอกแบบฟอร์มแทนเขียน SQL เอง (ความปลอดภัย 5 ชั้น)
  3. ทำไมเลือก bge-m3 (รองรับหลายภาษา ผู้ใช้ถามไทยแต่บทความเป็นอังกฤษ)
  4. ทำไมไม่ใช้ pgvector (มีแค่ ~1–2k chunk การสแกนทั้งหมดเร็วพอ)
  5. Chunking ตามหัวข้อ + overlap 15% + ใส่หัว "Breed | Section" นำหน้า chunk
  6. `min_score` floor และการห่อผล tool ว่าเป็น untrusted data
  7. ตัวหยุด `max_steps` และการตรวจจับการเรียก tool ซ้ำ
- **ข้อมูล:** 40 บทความ Wikipedia (CC BY-SA) + ~280 พันธุ์จาก dogapi.dog (MIT) ระบุจำนวน chunk ที่ได้จริง

## 3. Evaluation Setup (1 หน้า)

| ชุดทดสอบ | จำนวน | ใช้วัด |
|---|---|---|
| retrieval_set | 32 (EN 22 / TH 10) | Recall@1/3/5, MRR@10 |
| unanswerable_set | 10 (พันธุ์ที่ไม่มีข้อมูล 4 / นอกเรื่อง 6) | การเลือก min_score |
| agent_set | 22 | tool selection, SQL exec match, answer accuracy |

- **Baseline:** BM25 สำหรับ retrieval และ "โมเดลเดียวกันแต่ไม่มี tool" สำหรับทั้งระบบ
- อธิบายว่าเฉลยของคำถาม SQL คำนวณจากฐานข้อมูลตอนรัน
- ทุกการเรียกใช้ `temperature=0` และรันซ้ำได้ด้วยคำสั่งเดียว
- บอกข้อจำกัดว่าชุดทดสอบเขียนโดยผู้พัฒนาเอง จึงอาจมีอคติ

## 4. Results (1.5–2 หน้า)

**ตาราง A: Retriever comparison** คัดลอกตาราง 1 จาก `retrieval.md`

**ตาราง B: Chunk-size sweep** คัดลอกตาราง 2 แล้วเขียน 2–3 ประโยคว่าทำไมขนาดที่ชนะจึงดีกว่า โดยอิงจาก Lecture 5: chunk ใหญ่ไปทำให้เวกเตอร์เบลอ เล็กไปทำให้เสียบริบท

**ตาราง C: min_score sweep** คัดลอกตาราง 3 ชี้ให้เห็นว่าที่ 0.0 (ค่าเริ่มต้นแบบไม่คิด) ระบบปฏิเสธคำถามที่ตอบไม่ได้ได้ 0% แล้วค่าที่เลือกได้เท่าไหร่ นี่คือ "measured improvement over a naive default" ที่อาจารย์บังคับ

**ตาราง D: End-to-end** คัดลอกตารางจาก `agent.md` (agent vs baseline ไม่มี tool)

## 5. Failure Analysis (1 หน้า) ส่วนที่ได้คะแนนมากที่สุด

เลือกเคสที่ผิดจริง 2–3 เคสจากหัวข้อ "Failures" และ "Items the agent got wrong" ทุกเคสต้องมี 4 อย่าง
1. คำถามและสิ่งที่ระบบตอบจริง (คัดลอกมา)
2. สิ่งที่ควรได้
3. **สาเหตุ:** ผิดที่ชั้นไหน (retrieval / การเลือก tool / argument / การสรุปคำตอบ) และทำไม
4. วิธีแก้ที่น่าจะได้ผล

**เคสที่อาจเจอ** (ใช้ได้เฉพาะเมื่อเกิดขึ้นจริงในผลของคุณ)
- **พันธุ์ที่ไม่มีในคลัง เช่น Xoloitzcuintli หรือ Tibetan Mastiff:** คะแนน cosine อาจสูงกว่า min_score เพราะยังเป็นเรื่องสุนัขเหมือนกัน ระบบจึงดึงบทความพันธุ์อื่นมาตอบ แสดงว่า min_score แยก "นอกเรื่อง" ได้ แต่แยก "เรื่องเดียวกันแต่ไม่มีข้อมูล" ไม่ได้ วิธีแก้คือเช็กชื่อพันธุ์กับรายชื่อที่มีในคลังก่อนค้น
- **คำถามภาษาไทยที่ใช้ชื่อพันธุ์ทับศัพท์:** ดูว่า dense ค้นเจอไหม ส่วน BM25 จะได้ 0 แน่นอน
- **คำถามที่ต้องใช้สอง tool:** โมเดลเล็กอาจเรียกแค่ tool เดียวแล้วตอบเลย
- **ตัวตรวจคำตอบอัตโนมัติผิด:** คำตอบถูกแต่ไม่ตรงคำที่ค้น เป็นข้อจำกัดของ metric ที่ควรพูดถึง

## 6. Limitations and Next Steps (ครึ่งหน้า)

- คลังเอกสารมี 40 พันธุ์ ตารางมี ~280 พันธุ์ จึงครอบคลุมไม่เท่ากัน
- ชุดทดสอบเล็ก (32 + 22 ข้อ) ช่วงความเชื่อมั่นจึงกว้าง ผลต่างไม่กี่ข้ออาจเป็นแค่ความบังเอิญ
- ตรวจคำตอบด้วยคำค้น ไม่ได้วัด faithfulness โดยตรง
- **สิ่งที่ทำต่อได้:** LLM-as-judge วัด faithfulness, reranker, ตรวจชื่อพันธุ์ก่อนค้น, เพิ่มบทความ, streaming UI
